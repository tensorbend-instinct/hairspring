\title{\vspace{-0.4in}\textsc{Hairspring}: Models propose; software verifies\\[6pt]\large An agent harness that checks work, records evidence, recovers after crashes, and tests its own improvements}
\author{Tensorbend Instinct}
\date{September 2026}
\begin{document}
\maketitle
\begin{abstract}
A language model can write code, use tools, and say that a task is finished. Its confidence is not proof. Hairspring is an agent harness built around a simple rule: the model proposes work, while ordinary software verifies the result, records what happened, restores the run after a crash, controls what agents share and remember, and tests changes to the harness before installing them. This paper explains that design from the ground up. It compares five common agent designs, shows the failure each leaves open, and traces one Hairspring mission from goal to verified result. On a matched set of ten software-engineering tasks, using the same model family and host-side tests, Hairspring resolved nine tasks and a direct-loop baseline resolved three. Hairspring used fewer model steps, but about 7.5 times the wall time and 7.2 times the cost. This is one small, curated comparison, not a general leaderboard result. The evidence supports a narrower claim: independent checks and evidence-driven repair can recover work that a model's own judgment misses.
\end{abstract}

\section{The problem in plain English}
Most software agents repeat the same cycle: give a model a goal, let it use tools, show it the results, and stop when it submits an answer \cite{react,sweagent}. This works until the model is wrong about being done. It may run the wrong test, repair only the visible symptom, forget an earlier failure, or report success after a tool broke.

Hairspring separates doing the work from deciding what becomes official. The model may search, edit, run tools, start limited child agents, and revise its answer. It may not write the final pass result. Software checks run against the submitted files. A second model, started with fresh context, may look for a specific blocking defect, but it cannot override a failed test. One durable event record stores the evidence needed to inspect or resume the run.

The same rule applies beyond the final answer. An agent may propose a shared fact, a memory, or a change to its own instructions. Separate software decides whether to accept it. In this paper, the word \emph{authority} means only ``the power to make that proposal official.'' Figure~\ref{fig:authority} names each proposal and the software that makes the last call.

\paragraph{What this paper contributes.}
\begin{enumerate}
\item A plain comparison of five common agent designs and the unchecked failure each leaves open.
\item A complete mission path in which tests and a fresh review decide whether work passes, while one event record supports inspection and crash recovery.
\item Separate acceptance paths for shared state, memory, and changes to the harness.
\item A matched ten-task comparison, with raw per-task records and commands that recompute the reported totals.
\end{enumerate}

\section{Five common agent designs}
\label{sec:classes}
Figure~\ref{fig:classes} is a map of the field. The categories describe control-flow shapes, not named products. Real systems often combine them.

\begin{figure*}[t]
\centering\includegraphics[width=.97\textwidth]{figures/fig-classes.pdf}
\caption{Five common agent designs. The middle column says what each design does. The right column states the unchecked failure that remains. All five can do useful work; none, by shape alone, prevents a model's own mistake from becoming the accepted result or lasting state.}
\label{fig:classes}
\end{figure*}

\paragraph{Direct loop.} One model repeats think, act, and observe, then submits when it believes the task is done \cite{react,sweagent,minisweagent,reflexion}. This is simple and cheap. It also lets the worker grade itself, so a fluent wrong answer can cross the finish line \cite{selfcorrect}.

\paragraph{Fixed workflow.} A person draws a graph of model steps and branches before the run starts \cite{workflowblog}. This is predictable for known cases. A new situation may have no valid route, and a model-based checking step is still a model opinion unless an external test owns the result.

\paragraph{Model team.} Several copies of a model plan, debate, vote, or take roles \cite{selfconsistency}. Different wording is not independent evidence. Shared blind spots can win a vote, producing agreement without correctness \cite{consensus,cascades}.

\paragraph{Search or evolution.} A controller generates many reasoning paths, prompts, or policies and selects the highest-scoring candidate \cite{tot,treesearch,gepa}. This can be strong, but it fails when a candidate influences the judge or the model's confidence becomes the score. Cost also grows with the number of branches and trials.

\paragraph{Memory add-on.} A store retrieves notes from earlier runs and places them in the next prompt. This extends a model across sessions. Without validation and source tracking, a wrong note can become a lasting fact; relevance does not mean truth \cite{memfail}.

\paragraph{Shared problem.} In each shape, some model output can become accepted without a different mechanism proving it. Hairspring addresses that problem by giving each kind of proposal a separate acceptance path.

\section{What must be decided outside the worker}
Five questions appear in a long-running agent system. Each has a plain software owner.
\begin{description}
\item[Did the work pass?] Executable checks run on the submitted workspace. A fresh reviewer may block a result by naming a grounded defect.
\item[What happened?] A single event writer stores ordered model calls, tool results, file identities, costs, and verdicts.
\item[What may agents share?] A world service validates proposed shared state before other agents can treat it as accepted.
\item[What should be remembered?] A memory record keeps its source and later-use signal. A retrieved note is never relabeled as proven truth.
\item[Did a harness change help?] A scorer fixed before the trial compares old and new policies on held-out tasks and records why a change was kept or undone.
\end{description}
The worker can still be creative. These boundaries govern only what becomes a pass, official history, shared state, stored memory, or an installed policy.

\section{A mission from start to finish}
\label{sec:pipeline}
A mission begins with a goal, a project directory, available tools, success checks, and time and cost limits. The model works through typed tools. Each model call and tool result is recorded. When ready, the model submits both an artifact and the checks that should prove it.

The checker restores the workspace to the submitted state and runs those checks there. If a check fails, the failure evidence goes back to the worker for repair. If the checks pass, a fresh-context reviewer sees the goal and artifact, without the worker's explanation, and looks for a blocking defect. That reviewer can return a defect; it cannot turn a failed check into a pass. Only a clean check result plus no blocking finding creates a verified outcome.

\paragraph{Tools and files.} The kernel exposes one generated list of typed tools, so the prompt and the executable registry cannot silently disagree. Tool requests and results retain names, arguments, timing, outcome, and payload references. File edits use patches or anchored replacements. Commands run in an operating-system sandbox; startup fails if the required sandbox is unavailable.

\paragraph{Submission as one transaction.} The answer and its declared checks are persisted together before judgment begins. This prevents an answer from appearing final before its proof requirements are known. Checks run on the submitted workspace rather than an arbitrary current directory.

\paragraph{Fresh review.} The reviewer receives the goal and artifact in a new context. Its narrow job is to find a specific, grounded reason the artifact should not pass. It runs read-only in the production path. If the reviewer crashes or returns an invalid result, the mission does not pass.

\section{A record that can restore the run}
A chat transcript is not enough to resume real work. It may omit tool state, partial effects, spending, or limits. Hairspring stores typed events in order, places large payloads under content hashes, and gives only one component permission to append to the official stream. Tools return results to that writer instead of changing the record directly.

Recovery reads the last complete, consistent prefix. It detects and discards an incomplete tail, then restores the transcript, tool results, counters, file references, and billed cost. The mission continues under the same identity and limits. A restart therefore cannot erase a failed check or reset a budget.

\begin{figure*}[t]
\centering\includegraphics[width=.95\textwidth]{figures/fig-recovery.pdf}
\caption{Crash recovery. The durable prefix contains more than conversation: it includes tool state, file identities, counters, and cost. Replay restores the same mission; it does not ask the model to summarize and start over.}

\end{figure*}

\evidence{Storage tests inject incomplete tails, duplicate clock values, corrupt registry markers, dead tools, interrupted migrations, and replay after a policy change. These tests live in the crates at the evaluated source revision.}

\section{Child agents, shared state, and memory}
A parent may start child missions with explicit step limits. Each child has its own event stream, charges work to the parent, and must finish before the parent can close. A child cannot start more children because the delegation tool is absent from its executable tool list.

Children may propose facts or artifacts to a shared world service. Validation must accept the proposal before another child treats it as shared state. The service records reuse, making it possible to see whether one child found and used another child's accepted artifact \cite{swarmworld}.

Memory uses the same discipline. Every stored record keeps its source and mission identity. Later citation can raise a reuse signal; being served and ignored can lower it. This signal measures usefulness, not truth. End-to-end tests cover writing, retrieval, and cross-child reuse. The unmeasured question is whether a live model keeps selecting the right records as the store grows.

\section{Testing changes to the harness}
The worker repairs a task artifact. A separate outer loop can propose changes to prompts and policy files. Before the candidate runs, Hairspring fixes the scorer and held-out tasks before either policy runs. The existing policy and candidate then run under the same test. The record keeps both hashes, test conditions, traces, scores, decision, and reason.

A malformed or fabricated verdict scores zero, and a failed candidate is undone. The proposer never grades or installs itself. No live promotion records are checked in, so this paper claims only that the mechanism and its tests exist, not that observed promotions improved production results. Hairspring does not yet rewrite and safely promote its own Rust code.

\section{Evaluation method}
The evaluation separates four kinds of evidence. Source and unit tests establish that a mechanism exists and preserves local rules. Installed-path tests establish that the terminal, registry, sandbox, checker, and rendered state connect that mechanism to a real mission. Live artifact trials establish that a real model can produce an artifact that passes independent checks. Matched external evaluations compare harness outcomes under one shared judge. A large unit suite does not substitute for an installed-path result, and a live result does not establish a general benchmark claim by itself.

The principal comparison uses ten software-engineering tasks drawn from a live public benchmark, with the same model family and host-side fail-to-pass checks. Each system operated through its native interface. Raw records identify task, submission status, outcome, steps, wall time, and cost, and are checked into the repository. The comparison is a curated subset, not a leaderboard sample. There are no repeated seeds or confidence intervals.

\section{What the matched comparison measured}
\label{sec:measured}
The baseline is a representative of class C1: a public, purpose-built agent--computer interface scaffold that runs a direct loop and is widely used as a reproducible software-engineering baseline \cite{sweagent}. It is the right comparison because it is the strongest simple shape: no workflow graph, no role ensemble, no search controller --- just a well-built loop.

\system{}'s failure was a two-hour timeout on \code{deepset-ai/haystack-8619}. The successful runs ranged from 23 to 171 worker steps. The baseline's three passes were \code{conan-17092}, \code{haystack-8525}, and \code{conan-17129}. Several baseline failures reached a submission but failed host-side tests; others encountered missing evaluation dependencies. The shared host-side verdict remains the reported outcome.

The result supports one bounded mechanism claim: executable judgment followed by evidence-driven repair can recover tasks that a cheaper flat loop leaves unresolved. It does not isolate the independent contribution of every subsystem. An early controlled test of parallel execution produced no gain and was reverted. The paper does not attribute the benchmark result to parallelism.

The trade is visible. \system{} spends about 7.2 times as much money and 7.5 times as much wall time to judge and repair during the run, and recovers six additional tasks for it. The baseline remains simpler and cheaper when an external evaluator already supplies the final verdict and the job does not need recovery, memory, shared state, or self-improvement. Per-task records, including the corrected wall and cost columns, are in Appendix~\ref{app:pertask}.

\section{Defects that changed the design}
The highest-value defects crossed subsystem boundaries while local tests remained green. Four examples shaped the current test rule.

\paragraph{A dead tool surface.} A capability could exist in a crate while the production terminal never registered it. The fix required a test through the real registry and installed terminal.

\paragraph{A wrong production mode.} General missions accidentally used an amnesiac benchmark arm. Unit tests for both modes passed; only a live installed-path run exposed the selection error.

\paragraph{Recursive delegation.} The first delegation design allowed descendants to delegate further, so process growth was bounded only by the host. The repaired design removes delegation from a child's surface and adds an explicit spawn cap; an installed-path test now reproduces this failure class.

\paragraph{An impossible gate.} Missing test dependencies and strict marker settings caused the evaluator to collect zero tests while the agent kept repairing a correct patch. Preflight now proves that the gate can execute before a mission starts.

A related defect class is reward hacking of the close path: the model learned to convert repeated critic refutations into a pass under a retry ratchet. The fix made malformed or absent verdicts fail closed, and refutation counters now reset per mission. This is the failure expected when a model can turn its own review into a pass. The final verdict is therefore executable, not rhetorical.

These failures lead to one rule: a mechanism is not accepted because its crate test passes. Its regression must reproduce how a model reaches it through the installed terminal path, including registry, sandbox, project root, judgment order, and rendered outcome.

\section{What Hairspring does not yet coordinate}
Recent long-horizon research controllers organize work into strategy exploration, readiness gates, dependency graphs, and global verification \cite{colosseum}. Their strongest transferable idea is explicit control over when a strategy is mature enough to decompose and where a verifier's finding should return.

\system{} supplies lower-level services for such controllers: replayable state, executable checks, a fresh reviewer, bounded children, shared state, memory, cost accounting, and held-out policy tests. It does not yet implement that research-planning layer. Missions remain flat. Critic findings return as whole-mission gaps. Candidates are selected or compared rather than constructively synthesized with their objections. No typed dependency graph localizes a defect to the affected closure.

\section{Limitations}
\begin{enumerate}
\item The headline comparison contains ten curated tasks. It establishes a difference on that subset, not general software-engineering superiority.
\item Verification is expensive. On the matched subset, \system{} spent about 7.2 times as much money and 7.5 times as much wall time as the baseline.
\item The study has no repeated seeds and cannot estimate result variance.
\item Self-improvement changes prompts and policy artifacts, not the Rust implementation.
\item Memory writes, recall, and cross-child reuse are exercised end to end; live-model selection quality at scale is not measured.
\item Research planning is flat. Strategy readiness, typed dependencies, objection-preserving synthesis, and section-addressed repair remain unimplemented.
\item At the evaluated paper revision, the workspace test suite passed; current pedantic Clippy does not pass. Passing tests do not make a different quality gate pass.
\end{enumerate}

\section{What the separation changes}
Separating suggestions from decisions makes failures easier to read. A failed check is an execution fact, not an opinion about answer quality. A broken reviewer is a machinery failure, not a pass. A retrieved memory is a sourced note, not shared truth. A well-explained candidate policy is still only a candidate until the fixed test measures it.

This framing does not remove model error. It changes where error can become state. The worker may still choose a poor plan or spend too long on a dead end. The surrounding software can preserve evidence, enforce budgets, refuse an invalid finish, and return a specific defect for repair. Those properties become more important as missions grow longer because recovery and attribution costs rise with the amount of hidden state.

\section{Conclusion}
\system{} treats reliable agent work as a separation-of-responsibilities problem. Across five common agent designs, model output can still become accepted without independent proof. Hairspring uses a simpler rule: the model does open-ended work, while tests, a fresh reviewer, an event writer, validators, and a fixed scorer decide what becomes a pass, official record, shared fact, stored memory, or installed policy.

On one matched ten-task software-engineering subset, this architecture resolved more tasks than a representative direct-loop baseline while using fewer worker steps, more money, and more wall time. The result is narrow. The design lesson is broader: a longer loop does not make its own verdict safer. Long-running agents become easier to inspect, recover, and improve when the model proposes and software decides.

\section{Event and verdict flow}
The following abbreviated trace shows the intended ordering. Field names are illustrative; the executable schema in \code{hs-core} is authoritative.
\begin{verbatim}
mission.opened    { goal, project_root, provider, budgets }
model.requested   { step, context_hash }
model.responded   { usage, billed_cost }
tool.requested    { name, args_hash }
tool.completed    { status, payload_hash }
answer.submitted  { artifact_hash, declared_checks }
checks.completed  { status, evidence_hash }
critic.completed  { refuted, findings_hash }
mission.closed    { outcome: "verified" | "rejected" | "stopped" }
\end{verbatim}

A valid close follows persisted submission and judgment evidence. A replay reconstructs state from the ordered stream and content-addressed payloads. It does not ask the worker to summarize what happened.
